# 1.0 audit prompts

Thirteen audits, one prompt each, plus a synthesis prompt. Each prompt is meant to be pasted into a fresh session at the repository root. Every prompt relies on the common rules below, so the first line of each one sends the auditor here.

Planning only: nothing in this file has been run.

## Common rules

These apply to every audit.

**Scope of action**

- Read-only on source. Do not fix, refactor, commit or open a PR. The only file you write is your findings file.
- Write findings to `docs/audits/findings/<NN>-<slug>.md` (the name is given in each prompt).
- Read `AGENTS.md` first, then the docs your prompt names. The docs describe intent; the code is what you audit. Where they disagree, that is a finding.
- Counts, lists and statuses (components, families, support levels, consumers) come from the code — `packages/contracts/src/style-support.ts`, `packages/catalog/src/manifest.ts` and friends — never from a doc or from this file.

**Running things**

- Never run `pnpm check:foundation` or the full consumer matrix. Do not rerun whole suites that already pass just to see them pass.
- Run focused commands only when they prove or disprove a specific suspicion: `pnpm exec vitest run <file>`, one Playwright spec, one CLI invocation in a temp directory. Run `pnpm build:packages` first when a test imports `dist`.
- Never touch production: no requests that write to `https://ombelle-ui.vercel.app`, no production database, no publishing.
- Subagents are fine for wide reading. Verify what they report before it becomes a finding.

**What counts as a finding**

- A finding is something you verified: you read the code path end to end, or you reproduced it. State which.
- A suspicion you could not verify goes in a separate "Unverified" section with what would settle it.
- Do not report style preferences, things a linter would say, or restatements of known gaps already listed in `docs/web-alpha-readiness.md` (reference them instead, and say whether they still hold).
- Prefer twenty findings that matter over a hundred that do not. Rank them.

**Findings file format**

```markdown
# <Audit name>

Date, commit SHA, what was covered, what was not covered and why.

## Summary
Three to six sentences: the state of this area and whether it blocks 1.0.

## Findings
### <ID> <title>
- Severity: blocker | should-fix | nice-to-have
- Where: path:line (every location)
- What happens: the concrete failure or cost, with the input or state that triggers it
- How verified: read end to end | reproduced with <command>
- Suggested change: one or two sentences
- Effort: S | M | L

## Unverified
## Looked at and found sound
```

Severity: **blocker** means 1.0 should not ship with it (wrong output, data loss, security hole, broken documented journey, false public claim). **should-fix** means real cost but shippable. **nice-to-have** is everything else.

IDs are prefixed per audit (`CMP-01`, `CLI-01`, …) so the synthesis step can reference them.

## Suggested order

| Wave | Audits | Why together |
| --- | --- | --- |
| 1 | 01 contracts and compiler, 02 CLI installer, 07 security, 08 rate limiting | Correctness and safety; their fixes can change public behaviour |
| 2 | 04 component practices, 05 design fidelity, 06 accessibility, 09 glass | Catalog quality; they share the preview and specimen tooling |
| 3 | 03 installation journeys, 10 duplication, 11 tests and evidence, 12 public surface, 13 hosted ops | Best run after wave 1 fixes land, since they judge the result |
| 4 | 14 synthesis | Needs all findings files |

Audits within a wave touch nothing but their own findings file, so they can run in parallel.

## 01 — Contracts and compiler

```text
Audit the contracts and compiler packages of this repository for correctness before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/01-contracts-compiler.md with IDs prefixed CMP-.

Scope: schemas/, packages/contracts/src, packages/compiler/src, scripts/sync-schema.mjs, and the unit tests beside them. Context docs: docs/02-system-architecture.md, docs/04-presets-and-contracts.md, docs/decisions/.

The promise this code makes is: a validated preset or recipe always compiles to the same bytes, on any machine, and anything invalid is refused with a precise diagnostic before any output exists. Look for where that promise can break:

- Determinism. Anything that depends on object key order, Map/Set iteration over unsorted input, locale, line endings, platform path separators, time, or number formatting. Check canonicalize.ts and hash.ts against every place a hash is computed or compared.
- Validation gaps. Inputs the JSON schema accepts but the compiler mishandles; fields validated in one path (preset) and not another (recipe, component recipe, snapshot); unknown-field rejection; colour syntax edge cases in color-syntax.ts; size and depth limits on untrusted input.
- Schema and generated-type drift. Whether the generated TypeScript in packages/contracts/src can go stale against schemas/ without the build failing.
- Resolution and precedence. Merge order between family defaults, preset, component preset and recipe in resolve.ts; whether the documented precedence is what the code does.
- The style-support table. Whether compiler, CLI, snapshot service and editors really read one table, or whether any of them carries its own copy or special case.
- Diagnostics. Codes that are documented but never emitted, emitted but undocumented, or that point at the wrong JSON path.
- Snapshot identity. Whether two different inputs can produce the same snapshot identity, or the same input two identities, across versions of the compiler.
- Versioning for 1.0. What in the schema or the compiled output would be a breaking change to alter after 1.0, and whether it is versioned today.

Where a suspicion is cheap to test, write a throwaway script in the scratchpad that feeds the compiler the input and compare outputs; do not add tests to the repository.
```

## 02 — CLI installer safety and correctness

```text
Audit the CLI package of this repository for safety and correctness before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/02-cli-installer.md with IDs prefixed CLI-.

Scope: packages/cli/src (plan/, apply/, project/, registry/, snapshots/, main.ts and the file readers), plus tests/integration for the behaviours you question. Context docs: docs/05-cli-specification.md, docs/10-installation-and-theme-merging.md, docs/foundation-local-usage.md, and the "Installer safety and scope" section of AGENTS.md.

This tool writes into other people's projects. The contract is: planning never writes; applying is transactional; a modified file is a conflict that --yes does not override; a stale plan is refused; a failed apply can be recovered; dependency installs never run lifecycle scripts. Try to break each clause:

- Plan/apply separation. Any write, network side effect or dependency install reachable from planning or from --dry-run.
- Transactions. What is left on disk if the process dies between any two writes, if a write fails halfway, if the disk is full, if two CLI processes run at once. Whether recovery works from each of those states, and whether the lock/journal itself can be left corrupt.
- Conflict detection. Ways an edited file is overwritten without a conflict: line-ending changes, BOM, case-insensitive file systems, symlinks, a file deleted and recreated, a missing or hand-edited lock entry.
- Path handling. Whether aliases, components.json paths, registry item paths or snapshot contents can make the CLI write outside the project root (traversal, absolute paths, Windows drive letters and UNC, symlinked directories).
- Package managers. Detection when several lockfiles exist, workspaces and monorepo roots, Yarn Classic versus Berry, Corepack; whether the project's manager or lockfile format can be changed by accident; that the scripts-disabled flag is passed for every manager and every code path.
- CSS and theme merging. Whether the globals.css merge can drop or reorder user CSS, mis-parse valid CSS, or fail to be idempotent on a second run.
- Remote input. Everything fetched from the snapshot service is untrusted: validation before use, size limits, timeouts, redirects, origin pinning, behaviour offline or on a 5xx.
- Exit codes and JSON output. Whether they match the specification in every failure path, since scripts will depend on them after 1.0.
- Scope isolation. Component-scoped recipes and presets leaking into global project defaults, or the reverse.

Reproduce in a temp directory using the fixtures in fixtures/ and the built CLI. Record the exact commands in each finding.
```

## 04 — Component good practices

```text
Audit the component catalog of this repository for React and front-end good practices before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/04-component-practices.md with IDs prefixed CAT-.

Scope: packages/catalog/src/templates, packages/catalog/src/manifest.ts, component-slots.ts, shadcn.ts, the Base UI edition (docs/decisions/0005-base-ui-edition.md), and docs/components/. Edit nothing; generated.ts is output, not source.

Users own this source after installation, so its quality is the product. Judge the templates as code a senior React engineer would be handed:

- API consistency across components: prop names, variant and size vocabularies, defaults, data-slot and data-state attributes, className and ref handling, controlled versus uncontrolled patterns. Build a table and report the outliers.
- Naming and structure parity with shadcn where the project claims it, and with Base UI where that edition is used. Differences that are deliberate should be documented; the undocumented ones are findings.
- React correctness: effects that should not be effects, missing cleanup, unstable ids, hydration mismatches, anything that breaks under React strict mode, server components or the React compiler; "use client" present where needed and absent where not.
- Composition: components that cannot be composed the way their docs show, props that are swallowed, event handlers that are not merged.
- Native semantics and forms: correct elements, form participation, name/value/required/disabled behaviour, label association.
- Dependencies each template pulls into a user's project: whether each is necessary, pinned sensibly and licensed compatibly.
- TypeScript: exported types, any/as casts, props that accept more than they honour.
- Docs versus source: every documented prop, part and variant exists, and the reverse.
- RTL, reduced motion and text scaling handled in the template rather than left to chance.

Sample every component at least once; go deep on the complex ones (overlays, combobox, select, calendar, command, carousel, toast, data-entry controls). Say explicitly which components got a deep read and which a skim.
```

## 05 — Design fidelity and consistency

```text
Audit the visual design of this component library for fidelity to its own design system and consistency across style families, before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/05-design.md with IDs prefixed DES-.

Scope: packages/catalog/src/styles, packages/catalog/src/presets, the family decisions in docs/decisions/ (0003, 0004) and the family design specs in docs/superpowers/specs/, docs/03-components-styles-accessibility.md, and the rendered result in apps/preview.

Setup: pnpm build:packages, pnpm generate:preview, then start the preview through the preview tooling and look at real pixels. Screenshots are evidence; attach paths.

Each style family has a written intent. The question is whether every component, in every family, in light and dark, looks like it belongs to that family and to the same library.

- Token discipline. Hardcoded colours, radii, shadows, spacing, durations or font sizes in family styles where a token exists; tokens defined and never used; the same value expressed three ways.
- Family integrity. For each family, name its defining traits from its spec, then list components that break them (a rounded control in a square family, a soft shadow in a hard-shadow family, a border weight that differs from its siblings).
- Cross-component consistency inside a family: control heights, padding scales, focus ring, disabled treatment, invalid treatment, hover/pressed feedback, icon sizes, label spacing. Build the grid and report the cells that differ without a reason.
- State completeness: hover, focus-visible, active, disabled, invalid, selected, open, loading. Missing or indistinguishable states.
- Dark mode: states that vanish, borders that disappear, shadows that do nothing, contrast that drops.
- Density and sizes: whether sm/md/lg mean the same thing across components.
- Newer components versus the original twelve: whether the later catalog batches received the same care, or fall back to generic styling.
- Presets: whether each built-in preset is coherent and whether any produces an obviously broken component.
- The public site and editors (apps/www) against the library's own look: does the site that sells the library use it well.

pnpm test:specimen-audit exists and measures focus, clipping, overflow, label spacing and target size. Read its latest recorded results in docs/evidence/ rather than rerunning it; run a single family or component only to confirm a specific defect you saw.
```

## 06 — Accessibility

```text
Audit the accessibility of this component library and its website before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/06-accessibility.md with IDs prefixed A11Y-.

Scope: packages/catalog/src/templates and styles, apps/preview, apps/www (site, both editors, published-preset pages), docs/accessibility-review.md, docs/03-components-styles-accessibility.md, the axe and keyboard specs under tests/e2e.

The target is WCAG 2.2 AA plus the WAI-ARIA Authoring Practices pattern for each widget. Automated scans already exist and pass; do not rerun them wholesale. Your value is what they cannot see.

- For each interactive component, compare its keyboard model, roles, states and focus management with the APG pattern: arrow-key behaviour, Home/End, typeahead, Escape, focus return on close, focus trap, roving tabindex versus aria-activedescendant. Drive the preview with the keyboard and read the accessibility tree; do not trust the source alone.

- Target size (2.5.8), reflow at 320 CSS px, 200% zoom and text-spacing overrides, reduced motion, RTL.
- The coverage gap: which catalog entries have a browser spec with an axe scan and a keyboard test, and which have none. Produce the list from the code.
- docs/accessibility-review.md: which entries have a recorded human or assistive-technology result and which are blank. Do not fill them in; you cannot perform a screen-reader review. State clearly that manual NVDA/VoiceOver review remains owed and give the reviewer a prioritised list of what to check first, based on what you found.
- The website and both editors as products: landmarks, headings, skip link, colour pickers and sliders, drag interactions with keyboard alternatives, the sandboxed preview iframe's title and focus behaviour.
- Claims: any place the README, site or docs says "accessible", "WCAG" or "tested with" beyond what the evidence supports.
```

## 07 — Security

```text
Perform a security audit of this repository before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/07-security.md with IDs prefixed SEC-. Rate limiting and quotas are covered by audit 08; note anything you see there and move on.

There are three attack surfaces. Build a short threat model for each (who the attacker is, what they control, what they want) before looking for bugs.

1. The hosted service: apps/www (Next.js on Vercel, Postgres on Neon, SQLite locally). Read src/app route handlers, src/snapshots/server, src/recipe-snapshots, next.config.ts, vercel.json, docs/hosted-deployment.md, docs/snapshot-service-operations.md, docs/production-operations.md.
   - Anyone can publish a snapshot. Follow untrusted input from the request body to storage to every place it is rendered or served: validation, size limits, SQL construction, stored XSS in published-preset pages, content types, caching headers.
   - The preview iframe and compiler workers: sandbox attributes, origin isolation, postMessage origin and schema checks (src/editor/preview-protocol, src/snapshots/preview-session), whether user-controlled CSS or tokens can escape the preview or exfiltrate.
   - CSS injection specifically: colour and font values that end up in stylesheets, url(), @import, closing-brace breakouts.
   - HTTP headers: CSP, frame-ancestors, HSTS, referrer policy, CORS on the API.
   - Withdrawal and moderation: who can withdraw, how that is authenticated, whether withdrawn content is still reachable.
   - Secrets and configuration: env handling, what is logged, error messages that leak internals, the read-only monitoring role.
2. The CLI on a user's machine: packages/cli. Audit 02 covers path traversal and lifecycle scripts in depth; here, focus on the trust chain: what the CLI fetches, from which origins, how an install code maps to content, whether a malicious snapshot or a hostile network can make the CLI write code the user did not expect, add dependencies, or run anything.
3. Supply chain and release: the published @ombelle-ui/cli package contents (scripts/pack-cli.mjs), pinned dependencies and pnpm audit exceptions (find where they are recorded and judge each), .github/workflows (token permissions, pull_request_target, unpinned actions, secret exposure to forks), the npm publishing route and provenance, the security reporting route promised in the docs.

Also check: the font feature's handling of remote fonts and licences, and any code path that evaluates or dynamically imports user-influenced content.

For each finding give a realistic exploit scenario and what the attacker gains. Prove exploitability locally where it is cheap (local dev server, SQLite store); never test against production. Separate real vulnerabilities from hardening suggestions.
```

## 08 — Rate limiting, quotas and abuse resistance

```text
Audit the rate limiting, quotas and abuse resistance of this project's hosted service before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/08-rate-limiting.md with IDs prefixed RL-.

Scope: apps/www/src/snapshots/server (quotas.ts, client-key.ts, body.ts, service.ts, recipe-service.ts, http.ts, publication-http.ts, recipe-http.ts, postgres-store.ts, sqlite-store.ts, postgres-pool.ts, config.ts, errors.ts), the route handlers in apps/www/src/app that call them, scripts/bounded-map.ts and worker-budget.ts, vercel.json, docs/snapshot-service-operations.md, docs/production-operations.md, tests/hosted and tests/integration/snapshot-*.test.ts.

The service is public, unauthenticated and backed by a paid database. First write down, from the code, the complete table: every endpoint, method, whether it reads or writes, what limit applies, the window, the key the limit is counted against, and where the counter lives. Then attack that table.

- Client identity. How the client key is derived; which headers it trusts on Vercel and whether a caller can spoof them; IPv6 prefix handling; shared NATs and corporate proxies being locked out together; behaviour when the header is missing.
- Correctness under concurrency. Whether check-then-increment is atomic in Postgres and in SQLite; whether parallel requests can exceed the limit; what happens across serverless instances; clock and window-boundary behaviour.
- Coverage. Endpoints with no limit at all, including reads, the published-preset pages, preview assets and anything that triggers compilation or a database query per request. Whether a cheap request can cause expensive work.
- Global ceilings. Whether there is a total cap on stored snapshots, storage size or daily writes independent of per-client limits, and what happens when it is reached.
- Body limits. Whether the size limit is enforced before the body is buffered, on every write route, including chunked and compressed bodies.
- Failure modes. If the quota store is unavailable, does the service fail open or closed, and is that the documented choice. Connection pool exhaustion as a denial of service.
- Client contract. Status codes, Retry-After and error bodies; whether the CLI and the editors handle a 429 sensibly and tell the user what to do.
- Growth of the limiter's own state: cleanup of old counters, table bloat, indexes.
- Platform layer. What Vercel's firewall or WAF is configured to do versus what the application assumes, and whether the docs say which layer is responsible for what.
- Abuse beyond volume: content that should be withdrawn, enumeration of install codes, code length and entropy.

Test concurrency claims against the local SQLite store and, if .env.hosted.local exists, an isolated database through pnpm test:hosted-storage. Never load-test production.
```

## 10 — Duplication and over-engineering

```text
Audit this repository for duplicated code, dead code and over-engineering before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/10-duplication.md with IDs prefixed DUP-.

Scope: everything authored by hand — packages/*/src, apps/www/src, apps/preview/src, scripts/, tests/ helpers and configs, the eight playwright.*.config.ts and three vitest configs at the root, .github/workflows. Exclude generated output (packages/catalog/src/generated.ts, generated schema types, apps/www/public bundles, apps/www/src/generated) except to ask whether it needs to be committed.

The project grew slice by slice, each with its own spec, plan, evidence script and test file. Expect parallel implementations of the same idea. The goal is a smaller codebase that does the same thing, so every finding must name what gets deleted and what replaces it.

- Parallel pipelines. Preset versus recipe versus component-preset versus component-recipe in contracts, compiler and CLI (recipe.ts, component-recipe.ts, recipe-snapshot.ts, snapshot.ts and their -source, -styles, -schema siblings). Where are these the same algorithm with different types, and where is the difference real.
- Twin stores and services. postgres-store versus sqlite-store, service versus recipe-service, http versus recipe-http versus publication-http, editor versus preset-editor in apps/www. Shared logic that was copied instead of extracted, and divergences that look accidental.
- Per-component repetition: integration tests, e2e specs, fixtures and evidence scripts that are the same file with a different component name. Estimate what a table-driven version would remove.
- scripts/: prepare-*-consumer, *-evidence, build-hosted-* families. Which are still used by a package.json script, CI or another script; which are one-off leftovers of a past slice.
- Config sprawl: what actually differs between the Playwright configs and whether projects in one config would do.
- Dead code: exports nobody imports, flags never set, branches unreachable since a later slice, statuses kept "for future use". Prove each with a search for references.
- Over-engineering: abstractions with a single implementation, options with a single caller, validation performed three times on the same value, defensive handling of states that cannot occur, indirection that exists only for a test.
- Under-engineering that causes the duplication: a missing shared helper that five files reimplement (hashing, atomic writes, path normalisation, colour parsing, process spawning).
- Utilities duplicated between packages and scripts (scripts/write-atomic.ts, process.ts, bounded-map.ts against their equivalents in packages).
- Dependencies used once or replaceable by the platform.

Rank by lines removed and risk reduced, not by count. For the ten largest opportunities, give the files, the approximate line count involved and the shape of the consolidated version. Flag separately anything where the duplication is deliberate isolation (for example, scoped recipes kept apart from global defaults by contract) so nobody "fixes" it.
```

## 11 — Tests and evidence integrity

```text
Audit the test suite and the recorded evidence of this repository before a 1.0 release. Start by reading docs/audits/1.0-audit-prompts.md, section "Common rules", and follow it. Write findings to docs/audits/findings/11-tests-evidence.md with IDs prefixed TST-.

Scope: unit tests in packages/ and apps/www/src, tests/integration, tests/e2e, tests/hosted, tests/hosted-browser, tests/helpers, the vitest and Playwright configs, scripts/check-foundation.mjs and the foundation-* and *-evidence scripts, .github/workflows/ci.yml and foundation.yml, docs/evidence/.

Do not run the suites. Two questions: do the tests prove what they appear to prove, and do the documents claim only what was measured.

- Tests that cannot fail: assertions on mocks of the thing under test, snapshots regenerated on demand, expectations computed by the same code they check, conditionals that skip the assertion, try/catch that swallows failure, soft assertions never collected.
- Skipped, fixme, only, retried and quarantined tests, and opt-in suites that CI never opts into. List each with its reason if one is recorded.
- Timeouts and worker limits raised to make something pass (the docs mention several); whether each hides a real slowness or race.
- Risk coverage map. For each of these, name the test that would catch a regression, or say there is none: nondeterministic compiler output; overwriting a user-modified file; writing outside the project; a stale plan being applied; recovery after an interrupted apply; a lifecycle script running; a quota being exceeded under concurrency; an invalid snapshot being stored; preview and installed output diverging.
- What CI runs on every PR versus what only the local foundation gate runs; whether a PR can merge green while the gate would fail.
- The evidence chain: how a docs/evidence/*.md or *.json file is produced, whether it can be edited by hand without detection, whether it records commit, environment and browser versions, and whether stale evidence is distinguishable from current.
- Claim check.
