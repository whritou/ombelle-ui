# Managed Blocks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship four blocks (`login-01`, `settings-01`, `pricing-01`, `dashboard-01`) that render in every family and edition, install with `ombelle add <block-id>` as managed files, and then go live on the website after CLI 1.1.0 is on npm.

**Architecture:** Blocks are catalog entries (`packages/catalog/src/blocks/`) with their own id list in contracts. `compile()` gains a `blockIds` option that compiles the block's components and emits two `kind: 'block'` artifacts per block. The CLI accepts block ids in `add` and `update`, maps block files beside the `ui` folder, records them only in the lock's `artifacts`, and relaxes one rule: a component Ombelle installed and the user edited is kept, with a notice. Track 1 (Tasks 1–12) ships CLI 1.1.0. Track 2 (Tasks 13–14) branches after publication and builds the site.

**Tech Stack:** TypeScript ES modules, React 19, Radix and Base UI editions, Vitest, Playwright, pnpm 11.25.0, Node 24.19.0.

**Spec:** `docs/internal/superpowers/specs/2026-11-25-blocks-design.md`. Visual source: the "1.1 blocks — <Family>" boards on each family page of the Ombelle design canvas (https://claude.ai/artifact/1FMRGWoyJSwht9wATT838U).

## Global Constraints

- Block ids, exactly: `login-01`, `settings-01`, `pricing-01`, `dashboard-01`. They never collide with a component id.
- Eight families: flat, liquid-glass, minimalist, neo-brutalism, ombelle, organic, papier, retro-futurism. Two editions: radix, base. Two modes: light, dark.
- Block templates import only `react`, `lucide-react` (no brand icons) and `@/components/ui/<id>`. Sample data lives in one `const exampleData`.
- The product name in block copy is **Ombelle** ("Sign in to Ombelle", the Ombelle workspace…). Never "Acme" (decided 25 November 2026). Each block's compile test asserts the source contains no `Acme`.
- Every block has one `h2` (no `h1`), works at 320px with no horizontal scroll, and switches to its desktop layout from 768px.
- Example-only actions never send anything anywhere. They go through one local `showExampleNotice()` function, and the file's header comment says to replace it. Exact copy:
  - `login-01` submit: Alert "Example only: this form doesn't sign anyone in"
  - `settings-01` Save: Toast "Example only: nothing was saved"
  - `settings-01` delete confirm: Toast "Example only: no account was deleted"
  - `pricing-01` plan buttons and `dashboard-01` menu items: a Toast naming the action and saying nothing happened, starting "Example only:"
- Block CSS: layout only, preset tokens only, no colour literals. Selectors name `[data-block="<id>"]` or `[data-block-part="…"]`, never a component `data-slot`.
- Lock: `lockVersion` stays 1. No new top-level lock field. Block files are recorded in `artifacts` with `kind: 'block'`.
- Diagnostic codes are unchanged (`UNKNOWN_COMPONENT` keeps its name). The new notice codes are `BLOCK_COMPONENT_EDITED` and `BLOCK_COMPONENT_MISSING`.
- No change to the bytes of any existing component's output, specimen or stable hash.
- Dependency installs keep lifecycle scripts disabled. `--yes` never bypasses a conflict.
- Release: CLI `1.1.0` ships first. The site's `publishedInstaller` moves to `1.1.0` only in Track 2, after publication.
- Conventional Commits. This branch is `docs/blocks-spec`. Implement on `feat/managed-blocks`, branched from it (Track 1), and on `feat/blocks-site` (Track 2).

## Review Focus

1. **A shadcn project that already has its own `components/ui/button.tsx`** runs `add login-01`. Expected: the plan stops with `FILE_CONFLICT` on that path, offering `--overwrite` or `--beside`, and nothing is written. (Task 7, test `foreign component conflicts`.)
2. **A component the block needs was deleted after install.** Expected: `doctor` warns with `BLOCK_COMPONENT_MISSING`, and `update login-01` recreates it. (Tasks 7 and 8.)
3. **`add login-01` run twice.** Expected: the second plan is all `noop`, with the same lock bytes. (Task 7.)
4. **A Base UI project.** Expected: the block uses `render`, never `asChild`, and typechecks. (Tasks 3–6 compile tests; Task 10 Base consumers.)
5. **Unusual components paths:** `components.json` aliasing `ui` to `src/ui` or a root-level `ui`. Expected: block files go to the sibling `blocks` folder (`src/blocks`, `blocks`) and stay inside the project root. (Task 6.)
