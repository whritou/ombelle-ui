> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Password Field, Carousel, Aspect Ratio and Toolbar to the catalog, and Form, Fieldset and Checkbox Group parts to the shipped Field and Checkbox, in both editions and all five families, with recipes; then use Toolbar in the editor top bar.

**Architecture:**
- **Catalog:** follow the 0.7.5 primitives plan (`docs/superpowers/plans/2026-11-12-primitives-075.md`) for new components and the 0.7.5 variants plan (`2026-11-12-variants-075.md`) for parts added to shipped components: contract ids and schema branches; self-contained templates and per-family styles; compiler specimens and install gating; preview and website registration; docs.
- **Self-contained files:** templates never import other catalog components. Form lives in `field.tsx` and Checkbox Group in `checkbox.tsx` because they need those files' contexts. Password Field, Carousel and Toolbar draw the Input Group, Meter, Aspect Ratio and Dropdown Menu looks themselves, under their own slots, with each family's rules repeated.
- **Website:** `scripts/generate-www-ui.ts` compiles the components the site uses at build time; nothing compiles when a page loads.

**Tech Stack:**
- TypeScript ES modules and React 19.
- Radix: `@radix-ui/react-toolbar` 1.2.1 (new), `@radix-ui/react-dropdown-menu` 2.2.1 and `@radix-ui/react-checkbox` (already pinned).
- Base UI 1.9.0: `Form`, `Fieldset`, `CheckboxGroup`, `Toolbar`, `Menu` (all present in the installed package).
- Next.js 16 for `apps/www`. Vitest and Playwright.

**Spec:** `docs/superpowers/specs/2026-11-13-components-076-design.md`

### Task 3: Form

**Files:**
- Modify: `templates/field.tsx`, `base/field.tsx`; `component-slots.ts` (`form`, `form-error-summary`, `form-error-summary-title`, `form-error-summary-list`); `styles/field/{five}.css` through the generator; `ComponentsScenario076` in both edition scenarios (the board's "Save preset" form: Preset name `required`, Radius `type="number" min=0 max=48`, Description, and a button that sets the server error `{ name: 'A preset with this name already exists.', ghost: 'Unknown field error.' }`).
- Create: `packages/catalog/test/form.test.ts`.

**Interfaces:**
- `type FormErrors = Record<string, string | readonly string[]>`.
- `Form(props: React.ComponentProps<'form'> & { errors?: FormErrors; validate?(values: Record<string, FormDataEntryValue | FormDataEntryValue[]>): FormErrors | undefined; summaryAction?: 'saving' | 'submitting' })` (the native `action` attribute passes through): `data-slot="form"`. Without hydration, no `noValidate` is rendered, so the browser validates. After mount it sets `noValidate`. On submit: for each registered field, `control.checkValidity()` false gives `control.validationMessage`; then `validate(values)` with values from `FormData` (a repeated name gives an array); a field's constraint message wins over other messages. With errors: `preventDefault()`, show them, focus the summary (or the first invalid control when no summary). Without errors, the native `onSubmit` prop runs as usual. Base: the root is `@base-ui/react/form` `Form` with the merged errors passed to its `errors` prop.
- `Field` gains `name?: string`. In a `Form`, it registers `{ name, controlId, label }` (the label text from `FieldLabel`), and its `invalid` becomes `props.invalid || hasError(name)`. `FieldError` with no children renders the form's message for that field. A change or input event inside the field clears its error (Review Focus).
- Server `errors`: a new `errors` object replaces the shown server errors and shows them immediately; nothing else is reported before the first submit.
- `FormErrorSummary(props: React.ComponentProps<'div'>)`: renders nothing while there are no errors; otherwise `role="region"`, `tabIndex={-1}`, `aria-labelledby` its title (`data-slot="form-error-summary-title"`, the heading copy in Global Constraints), and a list of lines in the order the fields appear. A line for a registered field is `<a href="#{controlId}">` whose click focuses the control; a line for an unknown name is plain text (Review Focus). Summary lines use the copy rule in Global Constraints.

**Interfaces:**
- `Toolbar(props: React.ComponentProps<'div'> & { orientation?: 'horizontal' | 'vertical'; loop?: boolean })`: Radix `Toolbar.Root`, Base `Toolbar.Root`; `data-slot="toolbar"`. Items register `{ id, kind: 'button' | 'link' | 'toggle', label, pressed?, disabled?, groupType?: 'single' | 'multiple', activate(): void }` in context, in DOM order.
- `ToolbarButton`, `ToolbarLink`, `ToolbarSeparator`, `ToolbarToggleGroup(props: { type: 'single' | 'multiple' } & …)` and `ToolbarToggleItem`: the primitive's parts with their slots. Each item takes optional `menuLabel?: string`; its menu label is `menuLabel ?? aria-label ?? textContent`.
- `fitCount(widths: readonly number[], available: number, triggerWidth: number, gap: number): number` (exported, pure): how many leading items fit; if all fit without the trigger, all; otherwise as many as fit beside the trigger.
- `ToolbarOverflow(props: { label?: string; children?: React.ReactNode })`: rendered last; a ResizeObserver on the toolbar measures item widths and sets the overflowed items `hidden` (with `data-overflowed`). The trigger (`More` by default, Ellipsis icon) shows when any item overflowed or when it has children. Its menu lists overflowed items in order — a button as an item, a link as a link item, a single-group toggle as a radio item, a multiple toggle as a checkbox item reflecting `pressed` — then, after a separator, its own `ToolbarOverflowItem` children. Choosing an item calls `activate()`. When the focused item overflows, focus moves to the trigger (Review Focus).
- `ToolbarOverflowItem(props: { onSelect(): void; destructive?: boolean; disabled?: boolean; children: React.ReactNode })`: destructive items go last, after their own separator (the current `OverflowMenu` behaviour).
- Radix: the menu is `@radix-ui/react-dropdown-menu`; Base: `@base-ui/react/menu`. Both draw it under the `toolbar-overflow-*` slots with each family's Dropdown Menu rules repeated.
